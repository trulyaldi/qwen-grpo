## 4. Budget: predicted vs measured (`results/budget/residuals/qwen3-4b-final_150_v2.md`)

- **Memory.** The analytical prediction was made before any Qwen3-4B measurement. Per phase, it overestimates the nvidia-smi process figure by 0.2–0.75 GiB. Over the whole 60-update run, the measured peak (2.67 GiB) is 0.24 GiB above the analytical maximum (2.43 GiB). Headroom to the cap is 4.78 GiB.
- **Time.** Each step is PCIe-transfer-bound. The measured step takes 8.54 s, against a transfer bound of 8.48 s at the measured 12.23 GB/s (a ratio of 1.01). Async prefetch can only hide the small compute time.
- **Forecast vs result.** Calibrated on the 60-update run's acceptance (0.226), the forecast was 665 attempts and 0.83 h for 150 updates. The actual run took **672 attempts and 3211 s (0.89 h)**.

## 8. Takeaways for the report

1. The full pipeline (async L2L, streamed rollouts, checkpointed backward, kill/resume, CPU merge, eval) runs correctly on Qwen3-4B. Every correctness check and the real-model kill/resume pass, and peak memory is about 36% of the 8 GB cap.
2. The budget model holds up: steps are transfer-bound (measured 1.01× the PCIe bound), and the 150-update forecast matched within 1% on attempts and 7% on time.
3. Learning is real but small. AUC improves significantly, the invalid rate drops, and predictions become more balanced. The accuracy gain (+0.9 pp) is not significant at n = 1066.
4. The main limit is the sparse signal: 78% of batches have zero advantage because the base model already gets 88% right. Possible fixes: a larger G, harder prompts (filtering out ones the base model always gets right), or a higher temperature.
5. In this run, Soup caught a gameable reward and correctly flagged that there was no forgetting baseline. Its data and adapter checks never ran because of missing dependencies. That is an installation issue, not evidence about what those checks detect.
6. Not covered: DFlash (D0–D6), and a single orchestrated requirements matrix and verdict.
